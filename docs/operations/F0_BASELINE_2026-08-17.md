F1 code and migrations may be developed and verified only against a clean disposable database; deployment to `main` or `preview` is blocked.

1. **Deployed migration ledger divergence.** The Neon `main` branch has the Phase 1 tables and `preview` has the Phase 2 tables, but neither has `drizzle.__drizzle_migrations`. `db:migrate` must not run against either branch until the ledger is reconciled and schema equivalence is re-proven.
2. **F1 deployment gate.** No F1 migration may be applied to an existing shared branch while item 1 is unresolved. This blocks deployment, not isolated F1 implementation and verification on a disposable clean database.

### IMPORTANT

1. The Neon default `main` branch is not protected. Enable branch protection before any production migration workflow.
2. `README.md`, `CLAUDE.md`, and the Phase 2 plan contain lifecycle language that predates the committed Phase 2 implementation. Documentation must be updated as part of F1 handoff.
3. Browser tests authenticate with a seeded synthetic database session. They do not prove delivery or redemption of a real Resend email in a live deployment.
4. The preview database contains test residue (two owner rows, one active session, and usage records). The exact `OWNER_EMAIL` allowlist still fails closed for other emails, but preview hygiene should be restored through an approved cleanup workflow.
5. The current Content Security Policy permits inline script/style execution. This is not evidence of exploitation, but the allowance should be narrowed where Next.js/runtime constraints permit and continuously tested.
6. Generation cancellation produces expected server-side “destination stream closed early” noise. User-visible state persists correctly; logs should eventually distinguish expected cancellation from faults.

### NON-BLOCKING

1. Turbopack cannot bind its CSS worker port in this local managed sandbox. The webpack production build passes, and canonical Turbopack verification belongs in CI/Vercel.
2. No local `.env*` runtime file exists. This is correct for secret hygiene but means live local authentication/provider calls were not attempted.
3. The repository was clean at baseline except for the previously requested untracked foundational build-plan document.

## Security and data classification

Every constitutional or future memory record must carry one of these classifications:

| Class | Meaning | Model/context rule |
| --- | --- | --- |
| `PUBLIC` | Safe for deliberate public disclosure | Eligible when relevant |
| `INTERNAL` | Normal Atlas operating information | Eligible for the authenticated owner when relevant |
| `PRIVATE` | Personal or business information not intended for disclosure | Eligible only for the authenticated owner and explicit task need |
| `SENSITIVE` | Material requiring extra minimization and careful display | Excluded by default; requires an explicit allow policy |
| `HIGHLY_SENSITIVE` | Exceptional personal, legal, financial, or security-impacting material | Never automatically retrieved; protected workflow required |
| `SECRETS` | Credentials, tokens, private keys, session material, raw connection strings | Never stored as memory/knowledge, never sent to a model, never logged, never shown in Brain |

Classification enforcement must occur before retrieval/context compilation, not after model generation. Client-exposed environment variables are always public. Authentication tokens and provider/database credentials remain server-only.

## Supersession and deletion contract

- Constitutional records are append-only by version during normal editing. A newly activated version supersedes the prior active version; old versions remain auditable and are excluded from active context.
- Drafts may be physically deleted when no audit obligation exists.
- Owner-requested physical deletion must cascade through dependent source chunks, activation references, and safe trace metadata.
- Secrets discovered in content are rejected or redacted rather than preserved as historical versions.
- Tombstones may retain non-content identifiers and deletion timestamps only when needed to make deletion idempotent; deleted content must not remain recoverable through Brain or context compilation.

## Protected migration reconciliation procedure

The clean rehearsal established the authoritative Drizzle ledger values:

| Migration | SHA-256 / ledger hash | Journal timestamp |
| --- | --- | --- |
| `0000_lucky_iceman.sql` | `cb7cb5db11b55e6a9932318aae49df322e11d250e2ca2b979ac2e8da2f603adf` | `1786935383289` |
| `0001_dear_iron_monger.sql` | `4c226a4811b566462a1f4dc31e4e7332cc3a208c8e765463f275a2da388c19b0` | `1786948306904` |

Do not manually mark migrations as applied based only on table names. The approved reconciliation workflow is:

1. Protect the Neon production branch and capture branch IDs, schema dumps, row counts, and a restorable pre-change branch.
2. Compare every table, column, constraint, index, and foreign-key action with the matching committed migration snapshot.
3. On an isolated child branch, create the standard Drizzle ledger and insert only the hashes whose schemas are proven equivalent: Phase 1 for current `main`; Phase 1 and Phase 2 for current `preview`.
4. Run `db:migrate`, schema checks, owner-isolation integration tests, and the full browser suite on that child branch.
5. Review the exact SQL and evidence. Require explicit approval before changing a shared branch.
6. Apply the same ledger reconciliation through the protected database migration workflow, verify immediately, and retain the rollback branch until post-deploy validation completes.

Until this procedure is approved and completed, use a new clean disposable database for F1 migration and test work and do not mutate existing shared databases.
